**The reframe this lane runs on.** Every prior wave built forward and stopped at

**PRE-1 — which fork does this cluster assume?** `none`. Where a load's
dimension depends on an open horn, both horns' numbers are reported and the fork

because an inventory of what is *missing* does not depend on which side of a

computing that dimension rather than testing candidates?** This cluster searches
nothing; it computes the dimension. That is the whole method: rather than
building candidate source actions and testing them, count the argument list of
the unknown and drive the count down. The one computation performed here is
itself of exactly the PRE-2 shape — the council's unasked question is decided by
charging one extra exponent and reading off a quotient dimension (4 -> 5), not by
comparing objects candidate-by-candidate.

**PRE-3 — does success introduce a new un-owned object?** No.
`free_object_delta = 0`. Every `U` name below labels an object that already
exists in the repository, with a named filing artifact and a named owner. The
naming convention exists so downstream clusters stop writing "blocked on the
source action" and start writing `U4`.
