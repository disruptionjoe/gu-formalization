## 1. PREFLIGHT — seven lenses, run inline

**Lens 1 — information retrieval / corpus search.** The corpus is 3,781
markdown files. Recall and precision trade against each other violently:
`"next gate"` returns 556 files (template noise); `"requires a probe"` returns
0 (the phrase is not this repository's idiom). The retrievable signal is not
the *intention* to run a check — nobody writes "I will run this" in a
recoverable form — it is the *admission* that one was not run, plus the
*artefact* of non-execution (a named file that does not exist). Both are
mechanical. Design consequence: two orthogonal sweeps, one over language
(S2), one over the filesystem (S1), and never a single fused score. A third
sweep (S3) reads the inventories that already exist, so the ledger diffs
rather than duplicates.

**Lens 2 — technical debt and backlog management.** The classic backlog
pathology is that a list grows monotonically because nothing has an exit
condition other than "done". This repository has the opposite and rarer
pathology: it has *four* partial backlogs
(`SESSION-INDEX` §C, the mailbox drain pass, the packet index, the improvement
register) and no union, so an item can be live in one and discharged in
another with nothing comparing them. The measured proof is below: three of my
own inherited `LIVE` rows were already discharged in a file the inheriting
inventory never read. Design consequence: the ledger's primary contribution is
the **join**, and the join must be re-runnable, which is why the probe pins each
source inventory's row count.

**Lens 3 — audit and compliance.** An audit finding needs a *criterion*, an
*observation*, and a *disposition*. The failure mode is a finding with no
criterion — "this looks unfinished". So every row below names the exact
sentence that constitutes the commitment, and the exact file fact that shows
it was or was not discharged. Where I cannot produce both, the row is
`UNTYPED` and says why. Five rows are `UNTYPED` and I would rather ship five
honest unknowns than one confident resurrection.

**Lens 4 — archival science / provenance.** `AGENTS.md` requires that
negative results, counterexamples and superseded routes be *preserved*.
Preservation and currency are different properties, and an archive that
cannot distinguish them is a trap for exactly this kind of sweep: a superseded
route looks identical to a forgotten one at the level of "nothing cites it".
The discriminator is not citation count. It is whether a *later dated artifact
adjudicates the same object*. Every `SUPERSEDED` typing below cites the
adjudicating artifact by path; a row with no adjudicator is not superseded, it
is forgotten.

**Lens 5 — software archaeology.** The strongest available evidence of a
dropped commitment in this repository is a **named file that does not exist**:
plans here name their probe paths, so an unbuilt probe leaves a dangling
reference. But the same signature is produced by three benign causes — a file
that moved, a plan that was re-scoped and reused its slot names, and a
campaign that landed the content under new names. All three occur here. S1
therefore partitions on *basename existence anywhere in the tree*, and the
`RB1`–`RB7` slot-reuse case is asserted explicitly in the probe so a future
reader cannot mistake it for a gap.

**Lens 6 — epistemics of supersession.** The dangerous class is an item whose
premise died but whose text survived. The register
(`lab/sources/source-claim-register.yaml`, 110 claims: hard-core 48 /
auxiliary 51 / disavowed-by-source 11) is the authority. Before any row enters
the worklist I checked it against the eleven `DISAVOWS` rows. Two rows were
touched: the dark-energy collision (`SC-COS-02` — the phrase 'dark energy'
occurs nowhere in the 2021 draft) and the `Z/3` count receptacle
(`SC-GEN-01` / `SC-GEN-04` — the draft disavows nature having repeated a
generation three times, and declares the imposter not a true generation).
Neither row's *work* presupposes a disavowed claim — one is a literature read
typed `WRONG-TYPE` at intake, the other is an orientation-bit computation on a
normal bundle — but both carry the fence in the worklist and neither may be
reported as bearing on a GU source claim without a typed bridge.

**Lens 7 — instrumentation and observability.** The reason `PC-3` sat for four
days is not that anyone forgot; it is that nothing *watches*. The repository
has 407 gates in `process_gates/` and not one of them senses a specification
without an execution. §7 proposes the signature. Its honest limit is stated
there: the signature is cheap and noisy, and its false-positive class is
exactly the archive `AGENTS.md` requires be preserved.

**Pre-flight failure modes this artifact could commit, and the mitigation
applied:**

1. *Resurrecting a killed route.* Mitigated by the typing step, by the
   register check, and by the hostile pass in §6 — which found a 40% error
   rate in my own first-pass typing and is reported rather than repaired
   silently.
2. *Duplicating an existing inventory.* Mitigated by §2, which finds four and
   diffs against all of them; 26 of the 51 candidates come *from* them.
3. *Novelty inflation.* Nothing here is claimed new except the join, the
   typing, the two file-level defects in §5 rows 3 and 4, and the signature in
   §7. Exact-substring searches returned zero hits for several phrases; per
   discipline that is read as *unnamed*, not as new.
4. *Attacking a claim the source disavows.* Mitigated by Lens 6. `target_claim:
   NONE-NOT-A-KILL` — this artifact kills nothing.
5. *A worklist nobody can act on.* Mitigated by sub-typing `LIVE` into
   `CHECK` / `GAP` / `HYGIENE`, so the 20 runnable rows are not buried under
   15 that are not runnable. §9 says bluntly whether it worked.

## 7. THE DETECTION SIGNATURE — what a gate could sense

Nothing currently senses this. Here is the signature, stated precisely enough
to implement, in decreasing order of precision.

**D1 — dangling named probe (highest precision, implemented in this ledger's
probe as S1).** An artifact cites a path matching
`` `(tests|process_gates|scripts)/…\.py` ``; the path does not exist; **and**
its basename exists nowhere in the tree. Precision here is high because a
moved file keeps its basename. Current population: 76.

**D2 — orphaned check label.** An artifact defines a labelled check — a token
matching `[A-Z]{1,3}-?[0-9]{1,2}` introduced within `N` characters of a
specification verb (*"must"*, *"criterion"*, *"acceptance"*, *"exit"*) — and
that token occurs in **exactly one** file in the tree, its own. `PC-3` would
have tripped this from 2026-08-11 until `portfolio-correction-wave` cited it
on 2026-08-12. Lower precision than D1; needs a label-shape whitelist.

**D3 — self-admitted non-execution without a successor.** A file matches the
S2 regex, and no file with a *later* `created:` date names the same object.
This is the sweep that produced the 158 lines. It needs the "same object"
predicate, which is the hard part; the cheap approximation is co-occurrence of
the nearest backticked identifier.

**D4 — plan-slot residue.** A campaign artifact enumerates `k` numbered slots
with named outputs; fewer than `k` outputs exist. This is what exposed
`RB8`/`RB9`/`RB10`, and it is also what exposed the benign `RB4`–`RB7`
slot-reuse, so D4 must report the *partition*, never a bare count.

**D5 — stated dissolution condition with no watcher.** A canon or near-canon
file states a condition under which it dissolves; nothing monitors that
condition. This is worklist row 28 and it is the highest-value member of the
family, because its failure mode is a live wrong verdict rather than an unrun
check.

**Recommended composition.** D1 as a hard gate (cheap, high precision, and its
false positives are all repairable by an edit). D2 and D4 as *reports*, run at
queue-review cadence, never as gates. D3 never as a gate.
